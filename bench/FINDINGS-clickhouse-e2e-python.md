## 1. What was built

A ClickHouse driver for `r64-db-engine` that pulls into the Arrow IPC sink, and
an end-to-end proof that the bytes arriving in meshroad are the bytes ClickHouse
holds.

The driver is **e2e-proven, not reference-grade.** It is proven against a live
server for the full 14-column meshbench schema, but it carries no
`CLICKHOUSE_SPEC` and therefore no Gate A conformance / self-regeneration
coverage, which the Postgres reference driver does have. That is the same gating
the pgsql driver sat under before its §10 work. Also absent relative to the
reference: a driver-level security test mirroring
`tests/drivers/postgres/test_driver_security.py`. Identifier quoting is
implemented (backtick doubling) but not regression-tested.

## 2. Dataset and ground truth

`meshbench.perf_1m` (1,000,000 rows) and `meshbench.perf_10m` (10,000,000),
generated by `bench/make-dataset.sh`.

Deterministic **by construction**: zero `rand()`, zero `now()`, every column
derived from `cityHash64(number, k)` with a distinct `k`. The tables regenerate
byte-identically from the script alone, which is what allows
`bench/GROUND-TRUTH-clickhouse.json` to be committed as a fixed expectation
rather than re-measured each run. A parity miss downstream is therefore
unambiguously a pipeline defect and never dataset drift.

All integer columns are `Int64`, not the `UInt64` that `numbers()` yields
naturally. This is forced: the driver's coercion table maps `UInt64` to
`unsupported` and raises, rather than risk a signed-int overflow on the ramdb
side.

`scaled_amount_sum` is recorded twice. The campaign specified
`round(sum(amount)*100)`, but ClickHouse sums float64 in parallel and float
addition is not associative, so that form is in principle order-sensitive. The
file also carries `sum(toInt64(round(amount*100)))` — order-independent integer
arithmetic — and **that integer form is the authority** for the parity check.
Both agreed exactly and were stable across three consecutive reps on both
tables; the float form remains as a corroborating observation only.

## 3. Type mapping, and what it cost

| ClickHouse | Arrow | how |
|---|---|---|
| `Int64` | `int64` | native; no narrowing step exists to guard |
| `String` | `large_string` | **fell out of pandas 3.0's `string` dtype — not forced** |
| `LowCardinality(String)` | `dictionary<int32,string>` | sink `dictionary_columns`, explicit config only |
| `Float64` | `double` | |
| `Nullable(Float64)` | `double` + null bitmap | **already worked — see below** |
| `DateTime64(6)` | `timestamp[us]` | new opt-in `timestamp_unit` on the sink |

Two of the three expected problems were not problems, and finding that out by
measurement rather than by patching is the point:

- **`large_string` needed no code.** pandas 3.0.5's `string` dtype maps to Arrow
  `large_string` on its own. The sink's own tests already recorded that both
  `utf8` and `large_string` are correct and that meshroad reads both.
- **True NULLs needed no code.** `pa.Table.from_pandas` maps float64 NaN onto
  Arrow's null bitmap. The prediction was that `query_df` would land
  `Nullable(Float64)` as float64+NaN and that NaN-as-a-value would break the
  null discriminator. Measured: `score` arrives with `null_count = 20039` and
  zero NaN values. A planned change to `core/coercion.py` was therefore NOT
  made, because it would have been a no-op on observable output while touching
  the layer every driver shares.

`DateTime64(6)` was the one real gap: pandas has no microsecond-native path, so
it widens to `datetime64[ns]` and Arrow then reports `timestamp[ns]` against a
reference artifact carrying `timestamp[us]`. The fix is a `timestamp_unit`
option on `ArrowIpcSink`, deliberately **opt-in** rather than a blanket ns→us
default — a blanket cast would silently truncate any source that genuinely has
nanosecond resolution — and it is additionally a **safe** cast, so precision
loss raises rather than quietly rounding.

## 4. End-to-end proof (Gate C)

`tests/e2e/test_clickhouse_to_arrow.py`, 7 tests, `--integration`, nothing
stubbed, against the live `meshroad-ch` container.

Schema matched the meshroad reference artifact **field-for-field, 14/14**.
Aggregates matched source-captured ground truth **10/10 exactly**: count
1,000,000 · uniq_status 6 · uniq_region 8 · uniq_product_name 50,000 ·
status='active' 166,627 · region='West' 124,935 · sum_quantity 250,480,021 ·
max_account_id 3,599,999,873 · scaled_amount_sum 11,994,337,292 ·
score nulls 20,039.

Value checks are made against expectations **captured at the source**, because a
pipeline checked against its own output proves only that it is self-consistent.
For the same reason the test's ClickHouse oracle speaks raw HTTP rather than
going through the driver under test — a fixture that used the driver to verify
the driver could hide a defect on both sides of the comparison at once.

The atomic-swap test uses a purpose-built `swap_probe` table rather than
`UPDATE`-ing `perf_1m`, which would invalidate the committed ground truth and
break the dataset's regenerate-byte-identically property. Atomic swap is a
property of the sink, so a small table proves it identically.

### The null-semantics claim, proven to the end of the chain

This is the finding that survives furthest downstream, and it is worth stating
as its own claim: **SQL NULL semantics survive from ClickHouse into meshroad's
query engine, not merely into the Arrow file.**

A `Nullable(Float64)` column with 20,039 NULLs was pulled, coerced, written to
Arrow, mmap'd by a separate `meshroad serve` process, and queried over Arrow
Flight. Through meshroad's own DataFusion engine — an entirely independent
reader from the pyarrow path the e2e uses:

```
SELECT count(*)     FROM perf  ->  1000000
SELECT count(score) FROM perf  ->   979961
```

979,961 + 20,039 = 1,000,000, matching ground truth exactly. The discriminator
is that the two counts **disagree**. Had NULLs been filled with `0.0` in transit
they would agree, and every aggregate would still look plausible while being
quietly wrong. `count(*) == count(score)` is the failure signature; it did not
occur. `status='active'` independently returned 166,627 through the same path,
also matching ground truth.

### Live refresh, and why it was tested in that shape

The artifact was re-pulled underneath the running serve while DoGet was
hammered continuously: **316 calls, 0 failures**, with the served count moving
1,000,000 → 500,000 → 1,000,000 and the serve log confirming
`installed generation 2` then `generation 3`.

The 1M→500K→1M shape is deliberate. Proving only that the generation swapped
would be equally consistent with a server that drops queries during the swap;
proving only that queries never failed would be equally consistent with a server
that never noticed the new file. Both together, with the row count as the
discriminator, are what distinguish a working refresh from either failure.

## 7. Methodology

**Artifacts of record.** Both benchmark artifacts are pulled with an explicit
`ORDER BY row_id`, making them deterministic and locality-comparable to the
`row_id`-sorted meshroad lineage artifact. Byte-reproducibility was proven, not
assumed: two ordered pulls produced identical sha256, verified a third time on
restore. Verification is therefore **by checksum**, not by content.

| artifact | rows | size | sha256 |
|---|---:|---:|---|
| `perf.arrow` | 1,000,000 | 149,806,522 B | `db2912df…` |
| `perf10m.arrow` | 10,000,000 | 1,497,969,210 B | `640a7389…` |

**Lanes.** A_warm = meshroad Flight DoGet against a long-running serve,
post-prefault with a discarded `count(*)` warmup. A_cold = same, against a fresh
serve process per rep. B1 = Python load+compute, fresh process per rep, `uv run`
with pyarrow==25.0.0 / pandas==3.0.1 / numpy==2.4.3, `memory_map` + `to_pandas`.
B2 = compute-only against a DataFrame preloaded once. C = ClickHouse itself via
`clickhouse-client --time`.

**Pairing.** For each op, each rep runs A_warm / B1 / B2 / C back to back before
the next rep begins, so cross-lane ratios are formed from samples taken seconds
apart rather than blocks minutes apart. Machine drift then moves both sides of a
ratio together instead of inventing one.

**A_warm includes the gRPC DoGet round-trip**, a floor of roughly 1 ms, whereas
B2 is in-RAM compute only with no protocol at all. **B2 beating A on trivial ops
is protocol overhead, not an engine deficit**, and must be read that way.

**"Cold" means meshroad's column cache is empty, not that the OS page cache is
cold** — the file stays in page cache throughout. This is the same definition
`meshroad stats` uses. Cold numbers are not disk-read numbers.

### Doctrine amendment (ratified): quiet-baseline once, foreign-contention per invocation

The campaign doctrine originally required `loadavg < 1.0` before **every**
invocation. That gate is unsatisfiable by construction in a series that spawns
its own processes: lane B1 starts a fresh `uv` process per rep and lane A_cold
starts a serve per rep. Measured directly — **the series tripped the 1.0 gate at
loadavg 2.92 with zero foreign processes running.** The gate was not detecting
contention; it was detecting our own throughput and aborting on success.

Amended, and now permanent doctrine: a `loadavg < 1.0` **quiet-baseline gate
enforced once**, before any work, against a genuinely idle machine; thereafter a
**foreign-contention gate per invocation** — kill-list processes present, or any
non-campaign process over 15% CPU — with loadavg recorded at every gate point
for the record rather than used as the trigger.

The amendment immediately earned itself: the foreign gate caught real contention
(`nginx` at 200%, `perl` at 50%×2) **at loadavg 0.73**, which the numeric gate
would have waved straight through.

**Abort, don't label.** On gate failure the run aborts rather than continuing and
marking results indicative. A number taken on a contended machine is not rescued
by a footnote.

### Deviations from the campaign brief

1. **Op set.** The brief overrides the `bench.rs` canon in two places: canon uses
   `WHERE region='West'` and `max(score)`; the brief specifies
   `WHERE status='active'` (the dictionary-encoded column) and
   `MAX(account_id)` (int64, the PG-001 lineage type). The brief was followed.
   **Lane A figures for those two ops are therefore not comparable to previously
   published bench.rs numbers.** `DISTINCT product_name` uses the canon's
   `count(distinct …)` form so the result stays scalar and the lanes compare
   like-for-like rather than measuring a 50,000-row transfer.
2. **`--refresh-ms 0` on cold serves**, so the refresh poller cannot touch the
   cache mid-measurement. This differs from the production serve configuration,
   which polls every 1000 ms.
3. **Per-rep counters for lane A are unavailable by design.** Verified against
   the live serve: `list_actions` advertises only `upsert`, and
   `DoAction("stats")` returns `unknown action` — the read-only stats surface was
   specced but never wired. Exposing it is an engine change, and the meshroad
   engine is frozen for this campaign. Counter evidence therefore comes from
   `meshroad stats`, and the per-rep counter column is reported as
   unavailable-by-design rather than silently dropped.

### Reading these honestly

**B1/A (10×–127×) is an engine-vs-interpreted-workflow number, not a kernel
number.** It must never be conflated with the 72,924× kernel-scoped claim. Most
of it is not compute at all: B1's `to_pandas()` materializes all 14 columns
while meshroad's projection pushdown touches only the ~5 an op needs. B1 is
almost flat across ops within a scale (115–142 ms at 1M) because it is dominated
by that fixed load, which is precisely why B2 is reported beside it.

**Python beats meshroad on the cheapest ops.** B2/A is **0.37×** on FILTER at 1M
and 0.85× on SUM. This is protocol overhead, not an engine deficit: lane A warm
includes the gRPC DoGet round-trip, a floor of roughly 1 ms, while B2 is in-RAM
compute with no protocol at all. Below that floor meshroad cannot win, and the
comparison is only unassailable because both B1 and B2 are shown.

**ClickHouse and meshroad straddle 1.0 in both directions, exactly as the
framing law predicts.** meshroad leads on DISTINCT (2.06× at 1M) and on
GROUPSUM/SUM/MAX at 10M (1.8×–2.3×). ClickHouse wins GROUPSUM at 1M outright
(1.04×, effectively tied) and **wins UPPER decisively at both scales — 0.37× and
0.18×, i.e. ClickHouse is 2.7× and 5.6× faster.** That is reported here as a
loss, not rounded away. Note the op uses DataFusion's builtin `upper`, per the
campaign op set; meshroad ships a dictionary-aware `meshroad_upper` and a
dedicated `upper-bench` subcommand precisely because builtin `upper` on a
dictionary column is its weak path. `meshroad_upper` was NOT measured here, so
this figure is the honest builtin-vs-builtin comparison and not meshroad's best
available answer for that op.

### Asymmetry gate — SUM/MAX cold→warm

| op | scale | cold | warm | cold/warm |
|---|---|---:|---:|---:|
| SUM(amount) | 1M | 2.64 | 1.34 | 1.97× |
| MAX(account_id) | 1M | 2.75 | 1.42 | 1.93× |
| SUM(amount) | 10M | 4.29 | 2.75 | 1.56× |
| MAX(account_id) | 10M | 4.33 | 2.89 | 1.50× |

These ops decode almost nothing, so a cold→warm delta **cannot** be a
decode-cache win and is attributed rather than claimed. On `powersave` the same
measurement showed 5.00× and 4.76×; switching to `performance` collapsed it to
~1.5–2.0×, which identifies most of the original gap as **CPU frequency ramp on
a fresh process**, not cache behaviour.

The residual ~1.5–2× is a **design limitation of this lane**, stated plainly:
lane A cold starts a fresh serve per rep, so every cold sample is the FIRST query
in a NEW process and bundles DataFusion planning, catalog construction, allocator
and gRPC connection setup together with the cold column cache. The cold column
therefore measures process-cold, not purely cache-cold. Isolating the two needs a
warmup query against a different column set before the timed op; that redesign
was identified but deliberately not made mid-campaign.

### Residual spread

Three lane/op combinations exceed 20% at each scale, none of them lane A warm.
At 1M all three are lane A cold (20.0%, 37.8%, 22.4%) — expected, since each
cold rep pays fresh-process cost. At 10M they are B2 FILTER (30.7%) and
ClickHouse DISTINCT/UPPER (20.0%, 25.0%).

**Lane C is quantized and its sub-10 ms numbers are not trustworthy.**
`clickhouse-client --time` reports milliseconds, so at 1M nearly every lane C
value is literally 2.00 or 4.00 ms and its apparent "spreads" of 20–25% are one
quantum of resolution, not variance. C/A ratios at 1M should be read as
order-of-magnitude only; the 10M lane C values are large enough to be meaningful.

## 9. meshbench cannot round-trip through `.ramdb` (int64 lineage, PG-001 class)

The campaign intended a Row64 `.ramdb` lane. It cannot be run on this dataset,
and the reason is itself the result.

`account_id` is generated as `2e9 + cityHash64(number,1) % 1.6e9`, so it spans
2.0–3.6 × 10⁹. Signed int32 stops at 2,147,483,647. Measured at the source:

| table | rows over int32 | of | % over | max_account_id |
|---|---:|---:|---:|---:|
| `perf_1m` | 907,405 | 1,000,000 | **90.74%** | **3,599,999,873** |
| `perf_10m` | 9,078,525 | 10,000,000 | **90.79%** | **3,599,999,977** |

**~91% of rows carry an `account_id` that signed int32 cannot represent**
(`int32_max = 2,147,483,647`).

The pipeline does not corrupt them. `_raise_on_codec_unsafe_int64`
(`core/ramdb_writer.py:161`, raising at `:170`, bounds at `:44-45`) refuses the
write with `Row64CodecOverflowError` — **a loud refusal exactly where
row64tools alone truncates silently.** That guard is the difference between a
conversion that fails and a conversion that succeeds while quietly returning
`-746033870` for `3548933426`.

**These are ordinary production magnitudes, not an adversarial construction.**
A 10-digit account identifier is unremarkable — it is what account, customer and
order IDs look like in real systems once they pass ~2.1 billion, which any
monotonic ID generator does early in its life. The dataset was not built to break
the codec; it was built to look like production, and it breaks the codec anyway.

That is the whole justification for `ArrowIpcSink` arriving as an int64-native
format rather than as another guard bolted onto a narrowing codec. Arrow's
int64 is a native 64-bit type: there is no narrowing step, so the defect class is
unrepresentable rather than merely detected. **This dataset demonstrates the class
is live on realistic data, not historical.** Cross-reference RF-001 (int32
truncation lineage) and PG-001, the seeded `duration = 3548933426` that returned
as `-746033870`.

### Scope of this claim — read the fence

This establishes **the signed-int32 integer-codec ceiling in the row64tools codec
path**, and nothing wider. It is specifically about how integer columns are
encoded on that path.

It does **NOT** support any broader statement that `.ramdb` cannot hold large
data — not about file size, row count, cardinality, string length, float range,
or total volume. None of those were tested and none are implicated. A dataset
whose integer columns all sit inside int32 would round-trip through `.ramdb`
without touching this finding.

## 10. Lineage — the three-way decomposition

These are the three distinct claims in this line of work. They are measured at
different scopes and **must not be combined into a single multiplier.**

**1. Engine compute.** The documented cross-operator figure: the op set at
roughly 21 ms against roughly 429 s on R64 Server. Carried forward from prior
work, not re-measured here. It is **cross-operator and was never paired** — the
two sides were not run back to back under a shared gate — so it is an
order-of-magnitude statement about engine class, not a controlled ratio.

**2. Kernel.** 72,924×, **register-scoped**, with the 2.44 ms retirement figure
standing. This is a kernel-level measurement and is the number most likely to be
misquoted. Nothing in Phase E supports or extends it; Phase E is end-to-end SQL,
which straddles 1.0 against ClickHouse and is a different scope entirely.

**3. Workflow.** This was to be the R1 `.ramdb` lane. **It is replaced by the
representability finding in §9.** The old workflow does not get a time here — not
a slow one, not a fast one — because it cannot run on this data at all. A missing
number for a refused conversion is the correct outcome; substituting a modified
dataset to obtain one would have measured a different thing and reported it as
this one.

## 11. Accepted as published — known limits not remediated

Three limits are accepted as-is in this document rather than fixed, each with
follow-up filed:

- **The lane A cold column measures process-cold, not cache-cold.** Each cold rep
  starts a fresh serve, bundling DataFusion planning, catalog build, allocator and
  gRPC setup with the empty column cache. A cache-cold-isolated lane (warm up on a
  different column set, then time the target op) is filed as follow-up alongside
  the meshroad stats `DoAction` item, since both concern observability of a
  running serve.
- **Lane C timing resolution.** `clickhouse-client --time` reports milliseconds,
  so C/A at 1M is **order-of-magnitude only**. `clickhouse-benchmark` is filed as
  the future instrument for sub-millisecond lane C work.
- **UPPER measures builtin `upper` only.** meshroad's dictionary-aware
  `meshroad_upper` was not measured, so the reported ClickHouse win on that op
  (0.37× at 1M, 0.18× at 10M) is builtin-vs-builtin. A single-op addendum
  comparing `meshroad_upper` is future work.

## 12. What this does NOT show

- **No end-to-end performance claim is made at all yet.** Phase E is pending.
- **Any future meshroad-vs-Python ratio is an engine-vs-interpreted-workflow
  number.** It must never be conflated with the 72,924× kernel-scoped claim.
  End-to-end SQL straddles 1.0 on GROUP-BY-dominated queries, and the partial
  data already showed lane A slower than ClickHouse on GROUPSUM. That is
  expected and will be reported as such.
- **Unordered-pull scan locality was not benchmarked.** The artifacts are
  `ORDER BY row_id` for determinism and lineage comparability, but an unordered
  full refresh is what the production shape actually emits.
- **The lineage artifact is not the same data.** meshroad's reference
  `perf_1m.arrow` carries `row_id` 1..1,000,000; meshbench carries 0..999,999. It
  is a *schema* reference — the types the zero-copy reader expects — so Phase E
  numbers are not directly comparable to prior runs on that artifact.
- **B1 loads the whole table** via `to_pandas()`, while meshroad's projection
  pushdown touches only the columns an op needs. That difference is a real

- **Neither driver streams.** Memory ceilings scale with table size, so these
